# M3 – Text and PDF import

Branch: `m3-import`. References: `PLAN.md` (M3), `PROMPT.md` §4 (write order), §5 (import pipeline), §7 (Import screen), §8 (performance), the `pdf-import-pipeline` and `audiobook-storage` skills (`.claude/skills/`), the `modular-architecture` skill §2–§6, §9–§10, the mockup `.claude/design/02-import-pdf.png`.

## Goal

A PDF picked from the phone becomes a book in storage, fully offline: the text is extracted page by page by pdf.js in a hidden WebView, cleaned, segmented into Romanian sentences and split into chapters by pure functions in `services/text`, and saved chapter by chapter through the M2 `BookRepository`. The first chapter is playable before the import ends, a killed app resumes the import, and scanned, protected, corrupt or cancelled imports leave no data behind. The Library list and the player are M4/M5; M3 only produces the stored book and the Import screen.

## Corrections to `PLAN.md` (reported, fixed in the plan commit)

1. **pdfjs-dist 6.5 is ESM only.** `legacy/build/` has only `pdf.mjs` and `pdf.worker.mjs`; there is no UMD file to drop into a `<script>`. "The worker inlined" means a build-time step that produces one self-contained HTML (pdf.js as a module script, the worker as a blob URL or through `workerPort`). The exact form is decided by the spike in step 7.
2. **`services/pdf` doesn't touch the file system.** `WebViewPdfExtractor` receives a `readChunk(offset, length) → base64` function, bound in `app/dependencies.ts` over a new `FileStore.readBase64`. So `services/pdf` stays storage- and Redux-free, and the lint rule "FS only in `storage/` and `repositories/`" holds without an exception.
3. **Missing primitives.** The import form needs a text field (title, author) and a select (voice language), which M1 didn't build. `TextField` and `Select` go into `shared/ui`, with the `abook://dev/ui` catalog and a11y tests, like the other primitives.
4. **Boot.** M2 marks every `processing` book `failed` at boot (`failInterruptedImports`). M3c replaces that with resuming from `processedPages`, as already noted in the M2 decisions; only a book that can't be resumed (missing PDF, invalid meta) still becomes `failed`.

## Decisions (assumptions; I report them if they change)

- **Header/footer statistics vs. streaming.** The skill's rule ("repeats on ≥ 50% of pages") needs all pages, but the import saves chapter by chapter. Header and footer candidates are computed on a sample window (the first ~20 pages, or all of them if fewer), then applied to every page. A resumed import recomputes them from the same window, so the result is the same as an uninterrupted import.
- **`processedPages` = the end page of the last saved chapter**, not the last extracted page. Resume restarts at the first page of the next chapter and never re-splits a saved chapter. The progress bar in the UI uses the extracted page (in the slice), not `processedPages`.
- **Chapter source is chosen once, at open:** the PDF outline gives the page ranges up front; otherwise headings (short line, larger height, `^(Capitolul|Partea|CAPITOLUL|[IVXLC]+\.?)\b`) are detected while streaming; otherwise a chapter every ~10 pages. A resumed import uses the same source.
- **The import starts as soon as a file is picked**, as in the mockup (extraction runs while the form is editable). "Adaugă în bibliotecă" writes title / author / language into `meta` and closes the modal; processing continues in the background, driven by a thunk, not by the screen.
- **Duplicate fingerprint:** file size + SHA-256 of the first 64 KB (`@noble/hashes`, which probably needs `ESM_PACKAGES` in Jest). It is stored in `BookMeta`, so the schema changes → migration `002` (idempotent, as required by the M2 runner) that leaves old books without a fingerprint.
- **Test PDFs** are generated by a script (a 300+ page text PDF with Romanian text, repeated headers and page numbers; an image-only "scanned" PDF; a password-protected one; a truncated/corrupt one). They live outside the app bundle and are pushed to the emulator; they never ship in a release build. The generated PDFs cover the failure cases; the real PDFs in `C:\ModDeInvatare\Book-PDF` (next section) cover real layouts.
- **Yielding:** the pipeline awaits between batches of 5 pages and between cleanup/segmentation batches, so the JS thread stays free. Parsing happens only in the WebView.

#### 2. Page types, headers and page numbers
- `services/text/types.ts`: `PageLine { text, y, height }`, `PageText { page, lines }` (the shape the WebView returns), `PageHeight` if the band needs it.
- `stripRepeatedHeaders(pages, sample)` (top/bottom band, digits replaced before comparing, ≥ 50% of the sample), `stripPageNumbers` (isolated numbers, `- 12 -`, `12 / 300`, Roman numerals alone on a line).
- **Tests:** table-driven with a book header + chapter header, footers with changing page numbers, a line that repeats in the middle of the page (kept), < 2 pages, empty pages.

**Done** (2026-11-19). Findings:

- **Line shape:** `PageLine { text, y, height }` with `y` = the baseline's distance from the top as a **fraction of the page height** (0–1), so band checks need no page size; `height` stays in PDF units (compared between lines for headings in step 6). The WebView normalizes `y` in M3b. The types live in `services/text/types.ts`; `services/pdf` may import them (`boundaries` allows service → service).
- **Two functions instead of `stripRepeatedHeaders(pages, sample)`:** `detectRepeatedHeaders(sample)` runs once on the first `HEADER_SAMPLE_PAGES` (20) and returns the set of signatures; `stripRepeatedHeaders(pages, headers)` applies it to every batch. That fits the streaming import and the resume (the same sample gives the same set). Shared helpers in `pageBands.ts`: top/bottom band = 10% of the page, `headerSignature` (whitespace collapsed, digits → `#`, lower case).
- **Threshold:** a band line is a header when it appears on ≥ `max(2, ceil(50% × non-empty sample pages))` pages, counted once per page. Empty pages don't dilute the share, and a 2-page sample needs the line on both. Alternating running headers (book title on even pages, chapter on odd ones) sit at exactly 50% and are found.
- **Page numbers only in the bands:** `12`, `- 12 -`, `12 / 300`, `12 din 300`, `pag. 12` (≤ 4 digits) in either band; Roman numerals only in the **footer**, because a lone `IV` at the top of a page is usually a chapter heading (step 6 relies on it). A number alone in the body (a year, a list item) is kept.
- **Coverage:** `collectCoverageFrom` = `services/text` only, with a **`global`** 100% threshold. A path key (`./src/services/text/`, or a glob) is never matched by Jest on Windows ("Coverage data … was not found", exit 1). `npm run check` now runs `jest --coverage`; checked that one uncovered function makes it fail. Widening `collectCoverageFrom` later raises the bar for the new folders too (comment in `jest.config.js`).
- **Pitfalls:** `noUncheckedIndexedAccess` applies to tests (`texts(...)[0]` is `string[] | undefined`; destructure with a default). The first `check` after the Jest config change hit the known `EPERM` on the transform cache; the rerun was green.
- **Tests:** 503 in 55 suites; `services/text` 100% statements/branches/functions/lines.

#### 3. Hyphenation and normalization
- `joinHyphenatedWords` (`cuvân-\ntul` → `cuvântul` only when the hyphen ends a line and the next line starts lowercase; keeps `d-na`, `într-o` mid-line, and a hyphen before an uppercase word).
- `normalizeDiacritics` (ş ţ Ş Ţ cedilla → ș ț Ș Ț comma below, collapsed whitespace, NBSP, soft hyphen removed).
- **Tests:** Romanian samples with both diacritic forms, compound words (`nord-est`), line-final hyphen before uppercase, empty text.

**Done** (2026-11-19). Findings:

- **`joinHyphenatedWords(pages)` works on `PageText[]`, not on a string,** because the join crosses line and page boundaries and the sentence's page must stay right. The whole word moves **up** to the line (and page) where it starts (`stri-` p. 12 + `găt din curte.` p. 13 → `strigăt` on p. 12); a line emptied by a join is dropped and the next line can join into the same one (`ne-` / `maipo-` / `menit`). Hyphens: `-`, U+2010 and the soft hyphen; never `–` `—` (dialogue), never before an uppercase letter, a digit or a dash. Joins across batch boundaries are the pipeline's job (it keeps the last page of a batch, step 13).
- **Clitics keep their hyphen:** a fragment without a vowel can't be a syllable, so `s-` / `l-` / `n-` + `a dus` → `s-a dus`; plus `într-`, `dintr-`, `printr-` (`într-o`). Known limit: a clitic split right at a hyphen whose fragment has a vowel (`mi-` / `e`, `ne-` / `am`) loses the hyphen (`mie`, `neam`); typesetters rarely break there.
- **Three character functions instead of one:** `normalizeDiacritics` (cedilla ş ţ Ş Ţ → comma below; decomposed `a`+breve, `a`/`i`+circumflex, `s`/`t`+comma below or cedilla → precomposed), `normalizeWhitespace` (soft hyphen and zero-width characters removed, every whitespace run → one space, trimmed; `\s` already covers NBSP, U+2000–U+200A, U+202F, U+3000), and `expandLigatures` (ﬁ ﬂ ﬀ ﬃ ﬄ ﬅ ﬆ, which pdf.js returns as single characters). No `String.prototype.normalize` (it needs Intl, not guaranteed in Hermes) and no `\p{…}` regexes: letter tests use `toLowerCase() !== toUpperCase()` (`letters.ts`).
- **Prettier 3.10 unescapes `\uXXXX`** in string **and regex** literals, so invisible characters (soft hyphen, combining marks, zero-width) end up literal and indistinguishable in the source. They are written as code points instead: `charFromCode(0x00ad)` in strings, `new RegExp('[\\u00ad…]')` (double escape) for regexes. A Node scan confirms `services/text` has none left outside comments and test titles. Lookup tables are `[from, to]` tuple arrays (Prettier also unquoted object keys into literal characters).
- **100% coverage shaped the code:** `map[key] ?? key` fallbacks and `array[i]?.push` are branches that can never run; replaced with `split/join` over the tuples and with each line carrying its page's output array.
- **Tests:** 580 in 58 suites; `services/text` 100%.

#### 4. Sentence segmentation
- `segmentSentences(text)` on `.` `!` `?` `…` followed by space + uppercase or a dialogue dash; not after the abbreviations (dl., dna., d-na, nr., pag., p., vol., cap., etc., ș.a., ș.a.m.d., prof., dr.) or initials (`I. L. Caragiale`); „…” quotes and `?!` stay with their sentence. The abbreviation list is a constant in its own file.
- **Tests:** dialogue with `—` and `–`, nested quotes, abbreviations at the end of a real sentence, initials, numbers (`3.5`, `1.000`), ellipsis mid-sentence, empty / whitespace-only text.

**Done** (2026-11-19). Findings:

- **Output is `{ text, start }[]`, not `string[]`:** `start` is the sentence's offset in the input, so step 6 can give each sentence the page where it starts (`sentencePages`) from the page offsets of the joined text. Sentences are trimmed; blank ranges produce nothing.
- **Rule:** a candidate is `[.!?…]+`, then closing quotes/brackets (`” " » ’ ' ) ]`, kept with the sentence), then whitespace. It is a boundary only when the next character, after opening quotes (`„ « “`) or a dialogue dash (`— – -`), is an **uppercase letter**. That one rule covers the narrator tag (`— Vino! — strigă mama.` stays one sentence), the lowercase continuation after quotes (`„Vino!” zise el.`) and the mid-sentence ellipsis, and refuses digits (`nota 3. 4 oameni`).
- **Abbreviations** (`abbreviations.ts`): the word before a **single** period, with opening punctuation stripped (`(n.r.`) and lowercased, is checked against a set: the skill's list plus common Romanian ones (`d-lui`, `ing.`, `str.`, `art.`, `î.Hr.`, months…) and a few English ones for `en-US` books (`Mr.`, `Mrs.`, `e.g.`). Any single letter counts as an initial (`I. L. Caragiale`, `p.`). After `...` or `?.` there is no abbreviation check (`etc... Apoi` splits). Accepted cost: a real sentence ending in an abbreviation or an initial (`reviste etc. Apoi`, `vitamina C. Apoi`) isn't split; `Capitolul I. Începutul` merges too, but chapter headings are found on lines before segmentation (step 6).
- **Lint:** `max-params` (3) made the boundary a `Candidate { at, punctuation, next }` object, and the sentence builder returns `Sentence[]` (0 or 1) instead of pushing into a passed array.
- **Tests:** 616 in 59 suites; `services/text` 100%.

#### 5. Long sentences
- `splitLongSentence(sentence, maxChars = 400)`: cut at the `;` or `,` closest to the middle, recursively; if there is none, at the space closest to the middle; never mid-word. Every part ≤ `maxChars` (the M2 chapter splitter relies on it).
- **Tests:** 401 / 399 characters, only commas, no punctuation, one giant word, idempotence on short sentences.

**Done** (2026-11-19). Findings:

- **Split points:** a `;` or `,` **followed by whitespace** (so the Romanian decimal comma `3,5` is never one), the mark staying with the first part; punctuation anywhere wins over a space nearer the middle, then the space closest to the middle; ties go to the earlier position. Parts are trimmed, so joining them with one space gives the original text back (tested on a ~1,800-character sentence).
- **Last resort:** a run of more than 400 characters without spaces (a URL, extraction garbage) is cut every 400 characters. "Never mid-word" holds whenever there is a space; the hard cut keeps the ≤ 400 guarantee that the M2 chapter splitter relies on.
- **Signature:** `splitLongSentence(sentence, maxChars = MAX_SENTENCE_CHARS)` → `string[]` (blank → `[]`). The parts of a split sentence get the page of the sentence's start in step 6: a 400-character sentence crosses at most one page break, so the second part may show the previous page. Accepted.
- **Tests:** 628 in 60 suites; `services/text` 100%.

#### 6. Chapters and chunks
- `detectChapters` in three files by source: `chaptersFromOutline`, `detectHeadingChapters` (regex + line height above the page median), `fixedPageChapters` (~10 pages); plus `buildChapterChunk(pages)` → `{ sentences, sentencePages }` validated against the M2 `ChapterChunk` schema, and `toChapter` for the `toc` entry.
- **Tests:** outline with nested entries and missing pages, headings in Roman numerals, a "Capitolul" inside a paragraph (not a heading), a PDF with no headings, a sentence that spans a page break (gets the page where it starts).

**Done** (2026-11-19). Findings:

- **One range builder for all three sources:** `rangesFromStarts(starts, pageCount)` turns `{ title, page }` starts into contiguous `ChapterRange { title, startPage, endPage }` that cover pages 1…`pageCount` exactly (sorted, first start per page wins, starts outside the book ignored). Pages before the first start (title page, preface) become a chapter of their own with an **empty title**; the UI names untitled chapters through i18n (M4), so `services/text` stays free of texts. The same function serves the streaming import: the pipeline collects starts as pages arrive.
- **Outline (`chaptersFromOutline`):** top-level entries, or the level below when the top has fewer than 2 entries on distinct pages (a single "Cuprins" root); `null` when neither level qualifies, which tells the caller to use headings. Entries without a resolved page are skipped; titles go through `normalizeWhitespace`. The extractor resolves destinations to pages (M3b).
- **Headings (`findChapterHeading(page, bodyHeight)`):** a line ≤ 60 characters, taller than `1.15 ×` the body height (`medianLineHeight`, the median of the non-blank lines), starting with `Capitolul` / `Partea` / `Cartea` (any case) or being an **uppercase** Roman numeral alone (`IV`, `XII.`; a lowercase `vi` is a word). A tall short line right under it is added to the title (`I — Glasul pământului`). Per page, so the pipeline can run it while streaming; it uses headings only when it finds at least 2 (step 13).
- **Fallback (`fixedPageChapters`):** every 10 pages, empty titles, the last chapter shorter; a nonsense size is clamped to ≥ 1.
- **`buildChapterChunk(pages)`** (headers and page numbers already removed): `joinHyphenatedWords`, then per line `expandLigatures` → `normalizeDiacritics` → `normalizeWhitespace`, then `segmentSentences` and `splitLongSentence`. Each sentence gets the page of the line where it starts, found from the line offsets in the joined text. Lines taller than `1.15 ×` the chunk's median are segmented **on their own**, so `Partea întâi` and `Glasul pământului` become sentences instead of merging into the first sentence (they have no final period). The result passes `chapterChunkSchema`; `toChapter(index, range, chunk)` builds the `toc` entry and passes `chapterSchema`.
- **M3a complete:** 19 small files in `services/text`, every function pure and ≤ 40 lines, 100% statements/branches/functions/lines (228 / 114 / 72 / 215). Tests: 686 in 63 suites.

### M3b – `services/pdf`

#### 7. Spike: pdf.js in a WebView (throwaway)
- Answers the two open rows of the risk table: legacy pdf.js 6.5 with its worker inside a WebView on Android, and where the HTML lives in RN CLI (an Android `assets/` file + the iOS bundle, vs. an inline string generated at build time and passed as `source={{ html }}`).
- Also checks: `originWhitelist`, no network (`INTERNET` exists only in debug, so a release build proves it), message size limits, speed on a 300+ page PDF.
- **Check:** text from page 1 of a real PDF arrives in RN on the emulator. The spike code is discarded; the decision and numbers are recorded here.

**Done** (2026-11-19). Spike on `emulator-5554` (Android 17, System WebView / Chrome 157, debug build), with a throwaway `abook://dev/pdf-spike` screen and a generated 320-page PDF (1.42 MB, Helvetica, running header, page numbers, a larger `Capitolul N` every 20 pages, Title/Author). Code removed after the run; nothing of it is committed.

**Decision: the HTML is a generated string, passed as `source={{ html }}`** (no Android asset, no iOS bundle resource, the same code path on both platforms). The build script reads `pdfjs-dist/legacy/build/pdf.min.mjs` (538 KB) and `pdf.worker.min.mjs` (1.33 MB) and embeds them **as base64** (no escaping problems with `</script>` or non-ASCII); the page decodes them into blobs and loads pdf.js with `await import(blobUrl)`, which gives its real ESM exports. Result: 2.38 MB of HTML.

**Decision: the "fake worker", not a Web Worker.** A page loaded from an HTML string has an opaque (`null`) origin, and Chromium refuses to start **any** Worker from a blob URL there (even a one-line probe fails with an empty `error` event); `getDocument` then waits forever. Setting `globalThis.pdfjsWorker = await import(workerBlobUrl)` makes pdf.js run its worker code on the WebView's main thread. That thread is not RN's JS thread, and the WebView is hidden, so it costs nothing visible. It doesn't depend on the origin, so it should behave the same in WKWebView (checked on iOS in M7). Plan B, not needed: a `baseUrl` for a real origin.

**Findings for the next steps:**

- **Typing bug in react-native-webview 14.0.1:** `class WebView<P = undefined> extends Component<WebViewProps & P>`, and `X & undefined` is `never` under strict TS, so every prop is rejected. Workaround: `WebView<object>` (JSX generic and `useRef<WebView<object>>`). Step 10 wraps it once in `PdfExtractorHost`.
- **pdf.js lines:** `getTextContent` items with `hasEOL` and an empty `str` produce empty lines; the WebView side drops them (step 8). Items are grouped into lines by baseline (`transform[5]`, tolerance half the font height); `y = (pageHeight − baseline) / pageHeight`, `height = |transform[3]|`.
- **Options:** `getDocument({ data, isEvalSupported: false, disableFontFace: true })`: no `eval` (CSP) and no font loading (text only).
- **Messages:** RN → WebView with `postMessage` (a 700 KB string per chunk went through fine); the page listens on both `window` and `document` (`message`), WebView → RN with `window.ReactNativeWebView.postMessage`.
- **Startup:** the first WebView start costs ~2 s and the HTML is 2.38 MB, so `PdfExtractorHost` mounts the WebView **on demand** (first `open`) and unmounts it after `close`, instead of at app start (PROMPT §8: first screen < 1.5 s). The HTML module is required lazily too.
- **Not tested here:** a password-protected PDF (no tool on this PC generates one): the test-PDF script in step 11 makes one, and `PasswordException` is checked there. iOS is checked in M7.
- **Practical:** in RN 0.88 `console.log` doesn't reach `adb logcat` (`ReactNativeJS`), so results were read with `uiautomator dump` and a screenshot; and a deep link sent right after the app restarts is lost during bootstrap (the M2 risk), so it has to be sent again once the app is up.

#### 8. WebView build and bridge protocol
- A build script (in `.claude/scripts/` or `scripts/`) that produces the self-contained HTML from `services/pdf/webview/` sources + `pdfjs-dist`; the output is checked in or generated before Metro, as the spike decides. A test fails if the generated file is stale.
- `services/pdf/protocol/`: message schemas `{ type, requestId, payload }` (zod) for `load-chunk`, `open`, `get-pages`, `get-outline`, `close` and the responses/errors; the same validation runs inside the WebView.
- `RequestTracker`: per-request timeout, cancel, late or unknown responses dropped. Pure, tested with fake timers.

**Done** (2026-11-19). Findings:

- **The WebView page is TypeScript** in `services/pdf/webview/page/` (`groupLines`, `readOutline`, `parseRequest`, `createRequestHandler`, plus `services/pdf/limits.ts`), with **only type imports** from the rest of the code base: it imports `WebViewRequest` / `WebViewResponse` / `PageLine` / `OutlineItem`, so the compiler checks the page against the same protocol types as RN. No bundler: `scripts/build-pdf-webview.js` compiles each file with `typescript.transpileModule` (ES2020), strips `import` lines and `export` keywords, concatenates them in a fixed order inside one strict function scope, and **fails on a name declared in two files** (they would silently shadow each other). A small bootstrap (decode base64, `import()` pdf.js, fake worker, message loop) lives in the script. pdf.js is in Jest only as fakes, so the page logic is unit-tested.
- **Generated, not committed:** `src/services/pdf/webview/generated/pdfWebViewHtml.ts` (2.38 MB) exports the HTML and a SHA-256 of every input (the page files, pdf.js, the script). It's gitignored, ignored by ESLint and Prettier, produced on `postinstall` and at the start of `npm run check`; `npm run pdf:webview` regenerates it. A test fails when the stored hash differs from the sources (stale page), and checks the compiled script parses (`vm.Script`), has no `import`/`export` left and no URL.
- **Validation:** zod on the RN side (`webViewResponseSchema`, a discriminated union; `parseResponse` logs and returns `null`, never throws). The page can't ship zod without a bundler, so it checks RN's requests by hand (`parseRequest`); the tests run every page response through the RN schema, so both sides agree. Deviation from the plan ("zod on both sides"): reported.

- **Cleanup in one place:** the thunk's `guarded()` catches any error, records the reason (unless the user cancelled), then `deleteBook` + `bookRemoved`, and always closes the extractor.

  - Every case is asserted on the fake repository: no meta, chapter, toc, library entry nor file (`isEmpty()`), and nothing in the library slice.
- **Cancel:** `cancelImport()` dispatches `importCancelled` and closes the extractor, which rejects a pending batch.
  - The pipeline also checks `isCancelled()` at every step boundary (`throwIfCancelled`: after the copy, after `createBook`, after open, before each chapter, before the toc, before the ready meta), so a cancel during a storage write never ends `ready`.
  - A cancel during the duplicate prompt has no pipeline running, so it removes the copy itself. A cancel with no import running is ignored and logged.

#### 15. Resume at boot
- A `processing` book with its PDF present resumes from `processedPages` after `PdfExtractorHost` is mounted; without the PDF, or with an invalid meta, it becomes `failed` (the M2 behavior). `failInterruptedImports` is narrowed accordingly.
- **Tests:** crash after chapter 2 → boot → the import continues from chapter 3 and the result equals an uninterrupted import.

**Done** (2026-11-22). Findings:
- **Write order change (reported):** the toc is now saved with every chapter: chunk → toc (the chapters so far) → `processedPages`, then the `ready` meta. The final `saveToc` is gone, because the last chapter already wrote the full toc.
  - Why: a resumed import needs the saved chapters' titles and page ranges, and the chunks don't hold them. Without the toc it would have to extract those pages again, the slow part. A toc during processing also lets M4 list the chapters of a book still importing.
  - Storage rule 4 still holds: the toc is written after the chunks it lists, and `ready` comes last.
- **Resume point** (`resumePoint`): after the later of `processedPages` and the last toc chapter's `endPage`.
  - A kill between `saveToc` and `updateMeta` leaves the toc one chapter ahead, never behind.
  - With no toc (a toc is written with every chapter, empty ones included), the import restarts from page 1 and overwrites what it saved.
- **How a resume reads pages:** it always reads the 20-page sample again (scan check, book headers, chapter plan), so it cuts and cleans exactly like an uninterrupted import. It then feeds only the pages after the resume point.
  - On a heading plan, the next chapter starts on a heading page, so the assembler starts clean there.
  - Tested on outline, every-10-pages and heading plans. The result (meta, toc, chunks, file, order) is equal to an uninterrupted import's.
- **Boot:** `failInterruptedImports` → `failUnresumableImports`. Only a `processing` book whose file is gone becomes `failed`; a book with an invalid meta is not in the snapshot (M2).
  - After hydration, `useBootstrap` dispatches `resumeImports(books)` without waiting: the app opens and the books resume one after the other.
  - `PdfExtractorHost` is rendered by `AppProviders` outside the `ready` gate, so the WebView can mount during boot.
- **Slice:** `importResumed` (from a finished phase) starts at `opening` with the form taken from the meta. Title and author count as edited, so PDF metadata doesn't overwrite them. It also sets `submitted` and `chaptersSaved` = the saved toc length.
- **When a resume fails or is cancelled,** the book is removed, like a new import (one rule: a failed import leaves nothing). While another import is running (or a duplicate waits), the resume is postponed to the next boot and logged.
- **Not checked on the emulator yet:** there is no import UI until step 17. The kill → relaunch → resume check on the real 522-page PDF is part of step 18.
- **Tests:** 984 in 91 suites. New ones:
  - the resume (3 chapter plans);
  - pages read on resume;
  - a kill before `processedPages`, and a kill after the last chapter;
  - `resumePoint`, `importResumed`, `resumeImports` (in turn, failure removes, postponed);
